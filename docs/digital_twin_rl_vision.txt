# Self-calibrating digital-twin RL vision (2026-11-27)

## 背景・問題意識

ゲームAI型の強化学習は、多くの場合シミュレーション内部で完結している。
物体位置・速度・物理パラメータが完全に分かり、センサー噪声や遅延もないため、
シミュレーション内では強くても現実へ移しにくい。

現実では、

- 物体位置はカメラ経由で不完全にしか分からない
- 摩擦・質量・サーボ特性がシミュレーションと違う
- センサーに噪声・遅延・欠測がある
- アームやグリッパが経年変化する

したがって、シミュレーションを静的な学習環境として使うのではなく、
現実の観測で常時補正される動的な世界モデルとして使いたい。

## 目標

カメラや各種センサーから現実の状態を継続的に取得し、その情報でシミュレータを
補正・同期しながら、AIが現実へ適応し続ける仕組みを作る。

これは自己較正型デジタルツイン (self-calibrating digital twin) に近い。

最終的には、

1. ロボットが環境を計測する
2. 測定結果がシミュレータへ自動反映される
3. 更新されたシミュレータで強化学習・評価する
4. 実機とシミュレータを並行実行して状態を推定する
5. ズレを検出したら再較正・再学習する

という自律的な開発ループを目指す。

## 事前学習の位置づけ

完全に事前学習なしで実機だけで学ぶのは、試行回数・安全性・時間の面で非現実的。
目標は「事前学習を完全になくす」ことではなく、

  人手による個別調整を最小化し、シミュレーション事前学習 + 実機オンライン適応で運用する

ことと定義する。

段階:

1. シミュレーションだけで事前学習して終了: 現状の baseline
2. 事前学習 + 実機オンライン適応: 目指すべき現実的な方式
3. 完全に事前学習なしで実機学習: 研究レベル。初期目標にはしない

## 計算機構成

外部PC方式を初期案とする。ロボット側はセンサーと低レイヤ制御を担当し、
強い外部PCでシミュレーション・学習・状態推定・高級行動計画を実行する。

SSHは主にデプロイ・起動・ログ確認・メンテナンス用途。
リアルタイム通信はSSHではなく ROS 2 topic / DDS / gRPC / WebSocket などを使う。

オンボードPC方式は後の選択肢。遅延は小さいが、消費電力・重量・発熱・計算能力に制約がある。

## 強化学習の役割分担

全部を強化学習でやるのではなく、強化学習を正しい場所に使う。

- カメラから物体位置を推定する: 画像認識・状態推定
- 掴めているかを判定する: センサー融合・確率的状態推定
- シミュレータを現実に合わせる: システム同定・パラメータ推定
- どこへ手を出すか、どう掴み、どう運ぶか: 強化学習
- 滑りそうなときに掴み直すか判断する: 強化学習

掴持確認そのものは強化学習ではなく推定問題。
その推定結果を使ってどう動くかを決めるのが強化学習。

## POMDP としての捉え方

現実では真の状態が直接見えないため、これは POMDP（部分観測マルコフ決定過程）になる。
ポリシーには真の状態ではなく、推定された状態とその不確かさを入力する。

将来の観測候補:

- 関節角度・関節速度
- グリッパ開閉幅
- グリッパ指令値と実測値の差
- サーボ電流・負荷・電圧・温度
- キューブA/Bの推定位置・姿勢
- カメラ認識信頼度
- 最後に観測できた時刻
- occlusion / 見失いフラグ
- 接触確率・掴持成立確率・滑り確率・喪失確率
- デジタルツインによる予測位置と実測とのズレ

## 掴持確認

「閉じろ」と命令しても、実際には複数の状態がありえる。

- 何も掴めていない
- 触れてはいるが滑っている
- 正しく掴めている
- 一度掴めたが落下しつつある
- 物体ではなくテーブルや指同士を掴んでいる

したがって、掴持確認は単純な成功/失敗ではなく状態推定問題である。

使える情報源:

- サーボ電圧: 補助情報。電池残量や他関節の影響が大きく単独では弱い
- サーボ電流・負荷: 掴持力や抵抗の推定に有効
- 指の実開閉幅: 物体幅に相当する開きで止まったか分かる
- 指令値と実位置の差: 接触によって閉じ切れないことが分かる
- カメラ: 物体がグリッパと一緒に動くか確認できる
- シミュレーション: 掴めている場合の動きや接触を予測できる
- 小さな持ち上げテスト: 物体が実際についていくか直接確認できる

掴持判定は段階に分ける。

1. 接触確認: 開閉幅・位置誤差・負荷上昇で判定
2. 掴持成立確認: 数mm〜1cm持ち上げ、物体が追従するか確認
3. 搬送中の滑り監視: カメラ・開閉幅・負荷・予測とのズレを監視
4. 放置確認: 負荷低下後、指を開いても物体が残るか確認

デジタルツインでは「掴めている世界」と「掴めていない世界」の両方を予測し、
実際のセンサー値がどちらをよく説明するか比較する。

## 強化学習への統合

シミュレーション内では、センサー値も疑似的に生成する。

- 接触力からサーボ負荷っぽい値を生成する
- 開閉幅に噪声を入れる
- カメラ認識位置に噪声を入れる
- 一定確率でカメラ欠測にする
- 認識遅延を入れる
- 摩擦・質量・サーボ応答をランダム化する

シミュレータは真値を知っているが、AIには真値を見せない。
ポリシーには noisy observation / estimated state / uncertainty を入力する。

これにより、ポリシーは例えば次を学習できる。

- まだ触れていないならもう少し閉じる
- 掴めているなら持ち上げる
- 滑っているなら少し下ろして掴み直す
- 見えていないなら無理に動かず観測し直す
- 掴持が弱いなら搬送速度を落とす

## 学習フェーズ

Phase 1: 現在の基礎学習
- 状態ベース観測
- grasp と stack を分離
- SAC + HER
- 位置噪声あり

Phase 2: センサー noise robustness
- カメラ位置誤差・欠測・遅延・サーボ応答差を入れる
- noiseなし学習とnoiseあり学習を比較する

Phase 3: 掴持状態の導入
- 接触・掴持・滑りをシミュレーション内で判定する
- 最初は真値に近い情報を入れ、その後ノイズ付き推定値へ置き換える

Phase 4: 実機センサー対応
- 実機で開閉幅・負荷・電流・電圧・カメラ認識位置を記録する
- シミュレーションの疑似センサーと分布を比較する
- ズレがあればシミュレータ側の噪声モデルを修正する

Phase 5: デジタルツイン運用
- 実測値・シミュレーション予測・不確かさを統合して状態を推定する
- その推定状態でポリシーを動かす

## 報酬設計の方向

初期は sparse + HER を baseline とする。
grasp task の成功条件は例えば、

  キューブが規定高さ以上に持ち上がり、一定時間落下も滑りもしていない

とする。simulationでは真値で判定し、realでは推定値で判定する。

将来的には、過剰な掴持力を避ける、滑りを早期に検出して掴み直す、
見えないときに慎重になる、といった報酬も検討するが、最初は入れすぎない。

## 今日の最初の実務テーマ (2026-11-27)

実機センサーのチェック・調査。

最初の実験として、

1. 掴持時のサーボ負荷・開閉幅・電圧・電流を記録する
2. 空掴み・成功・失敗・滑り・テーブル接触をラベル付けする
3. カメラで小型リフト中にキューブが追従するか確認する
4. 実測センサー分布をシミュレーションの掴持状態と比較する

これはRL以前の実機計測ツールとして使え、後でデジタルツインの掴持推定器へ発展させられる。
